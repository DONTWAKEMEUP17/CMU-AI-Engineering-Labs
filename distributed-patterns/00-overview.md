# 00 · Overview — 为什么"都叫分布式"但每家不同

## 一段大白话开场

"分布式系统"这词被滥用到几乎没意义。同一个标签底下：

- **Kafka** 关心的是"几十个上游 × 几十个下游怎么传消息不变成蜘蛛网"
- **Redis 主从** 关心的是"我的内存 KV 单机扛不住读 QPS，能不能多几台机器一起读"
- **MySQL 复制** 关心的是"我的主库挂了不能让业务全停，要有个备用主库随时顶上"
- **ResilientDB / 区块链** 关心的是"节点之间互相不信任（可能恶意），还能不能让所有人对账本达成一致"

每家解决的痛点不一样、付出的代价不一样、适合的业务场景也完全不一样。**所以"分布式"不是一个技术，是一组针对不同痛点的技术家族。**

## 这套对比的 5 个维度

往下每一章都会按同一套维度回答同一组问题。读完 5 章再翻第 05 章那张对比表，所有方案的位置一目了然。

### 维度 1 · 这套方案到底要解决什么痛点

不要问"它怎么实现"，先问"它为啥被发明出来"。Jay Kreps 写 Kafka 时脑子里有的痛是"LinkedIn 内部几十个事件源对几十个下游变成 N×M 的对接蜘蛛网"。这跟 Redis 主从想解决的"单机内存 + 单核读不够"完全不是一类问题。**搞清楚 motivation 后，机制就是 motivation 的自然推论。**

### 维度 2 · 一致性 vs 可用性 vs 分区容忍（CAP 三选二）

每一家在 CAP 三角里站的位置不一样：

- **Kafka**：AP —— broker 挂一台读写继续，接受短暂复制延迟
- **Redis 主从默认**：AP —— 异步复制，主挂了 failover 可能丢最后几秒数据
- **MySQL 同步复制**：CP —— 主从都写成功才返回，可用性下降换强一致
- **ResilientDB / PBFT**：CP —— 所有 honest 节点对账本达成共识，可用性付出在共识轮次开销

### 维度 3 · 信任模型 — 节点之间互相信吗

- **Kafka / Redis / MySQL**：节点 honest —— 所有副本都听话，挂只挂在网络或硬件
- **ResilientDB / 区块链**：Byzantine —— 副本可能恶意撒谎，要靠多数票 + 密码学签名挡住

这一条是 BFT 共识 vs 普通主从复制最大的分水岭。复杂度成本完全不在一个量级。

### 维度 4 · 写吞吐 vs 读吞吐

- **Kafka**：写超强（顺序追加 log），读靠 partition 并行
- **Redis 主从**：读超强（多 slave 同时服务读），写还是单点
- **MySQL 主从**：跟 Redis 类似，读扩展、写单点
- **ResilientDB**：两边都不强 —— 共识轮次本身就是瓶颈，换的是 trustless

### 维度 5 · 典型业务场景

一句话回答："什么时候应该考虑它，什么时候不应该。"

- **Kafka**：事件流 / 日志总线 / 异步解耦。不适合做 OLTP 数据库。
- **Redis 主从**：热点缓存 / 排行榜 / 计数器 / session。不适合做长期持久化主存储。
- **MySQL 复制**：业务主库 + 读副本扩展 + 灾备。不适合存千亿级时序数据。
- **ResilientDB**：跨组织对账 / 区块链应用 / 不互信场景。不适合单组织内部数据库。
