## 1. 全景对比表

| 维度 | Kafka | Redis 主从 | MySQL 复制 | ResilientDB / PBFT | Caffeine（L1 本地缓存） |
|---|---|---|---|---|---|
| **解决的核心痛点** | N×M 集成耦合 → N+M pub/sub 解耦 | 单机内存/QPS 不够 → 读扩展 + HA | 单机挂了业务停 → HA + 读扩展 + 灾备 | 节点可能**作恶** → 共识仍然正确 | 反复查同样的数据 → 免网络调用 |
| **信任模型** | CFT（节点不会撒谎） | CFT | CFT | **BFT**（节点可能作恶） | 不涉及——本地内存 |
| **CAP 站位** | AP（可用 + 分区容错） | AP（默认异步） | AP（默认异步）/ CP（开半同步） | **CP**（一致 + 分区容错） | 不涉及——单进程 |
| **写吞吐** | 百万条/秒（顺序写磁盘） | 10 万 QPS（内存写） | 1 万 TPS（磁盘随机写） | 几百~几千 TPS（多轮签名） | 不涉及——只读缓存 |
| **读吞吐** | 高（顺序读 + 零拷贝） | 10 万 QPS（内存读） | 几千~几万 QPS（Buffer Pool 命中时） | 低（每读可能走一次共识） | **纳秒级**（本地内存，无网络） |
| **一致性** | 最终一致（ISR 内强一致） | 最终一致（默认）/ WAIT 后强一致 | 最终一致（默认）/ 半同步后接近强一致 | **强一致**（共识达成后才返回） | 取决于缓存策略（TTL / 主动失效） |
| **复制粒度** | partition offset（日志位移） | 命令流（AOF）/ 内存快照（RDB） | binlog event（行级变更） | 共识 block（一批交易） | 不复制——每进程独立 |
| **数据持久性** | 磁盘（按 retention 删） | 内存（RDB/AOF 只是兜底） | **磁盘（数据本体）** | 磁盘（每节点完整存储） | **不持久——重启即丢** |
| **典型业务场景** | 日志/埋点/CDC/消息解耦 | 缓存/计数器/session/排行榜/分布式锁 | **source of truth**——订单、支付、用户 | 区块链/跨机构清算/供应链 | 极热数据（配置、元数据、热点商品） |
| **不适合的场景** | 强一致交易、低延迟单条查询 | 当 source of truth（丢了赔不起） | 海量数据单表 > 千万行（要分库分表） | 同一管理域内部（太贵，Raft 就够） | 需要跨进程共享的数据 |
| **工程上手成本** | 中（partition 分配、consumer group rebalance） | 低（单机即开即用；主从/Cluster 中） | 中（Buffer Pool 调优、binlog 策略） | **高**（3f+1 部署、多轮签名调优） | 极低（一个 `LoadingCache` 就搞定） |

## 2. 为什么它们不能互相替代

> 这是面试里最容易出彩的一句话。"我学过 A 和 B——我知道它们不能互相替代，因为……"

### 2.1 为什么不用 MySQL 替代 Kafka

MySQL 能存消息（建张 `messages` 表），但：

- MySQL 是**随机写**（B+树 page 分散），Kafka 是**顺序写**（只往后追加）——写吞吐差两个数量级
- MySQL 的"消费"是 `SELECT`——随机读；Kafka 的消费是**顺序读**——consumer 顺着 offset 往下拉，磁盘顺序读 ~500MB/s
- MySQL 消息被读走后**没有"ack/commit offset"机制**——要么删（不能重播）、要么不删（consumer 崩溃后不知道从哪继续）

### 2.2 为什么不用 Redis 替代 MySQL

- Redis 重启没持久化 → **数据真的没了**。MySQL 重启数据在 `.ibd` 磁盘文件里
- Redis 没有 ACID 事务
- Redis 没有 SQL、没有 JOIN——缓存里不该存复杂关系数据

**Redis 是性能层，MySQL 是 truth 层。** 一个管"快"，一个管"对"。

### 2.3 为什么不用 Kafka 替代 Redis

- Kafka 的延迟是**毫秒级**（磁盘 + 网络），Redis 是**微秒级**（纯内存）
- Kafka 的数据模型是"不可变的日志"——不能 `INCR`、不能 TTL 到期自动删、不能 Set 去重
- Kafka 不是 key-value store——不能随机按 key 读当前值，只能按 offset 顺序消费

### 2.4 为什么不用 Raft（CFT）替代 PBFT（BFT）

- Raft 假设节点是诚实的——leader 不会给 A 和 B 发不同的 AppendEntries
- 如果节点可能作恶（跨机构、区块链）→ Raft 的多数派投票被叛徒控制 → 系统悄无声息地执行错误结果
- PBFT 每轮签名 + 三轮互广播 + 3f+1 的冗余量——成本高 10 倍，但**多了一种 Raft 不防的错误模型**

### 2.5 为什么还需要 Caffeine（本地缓存）

```
用户请求 → Caffeine（本地内存，0.001ms）
               ↓ miss
            Redis（同机房，0.5ms）
               ↓ miss
            MySQL（磁盘，5ms）
```

每一层 miss 的延迟差一个数量级。Caffeine 省的不是 Redis 的负载——**省的是网络往返本身**。极热数据（全局配置、首页热点商品）放在进程里，比 Redis 还快 500 倍。

## 3. 选型决策树

从"你遇到了什么痛点"出发：

```
你要解决什么问题？

├─ 服务之间发消息、解耦？              → Kafka
├─ 服务挂了不能丢数据？                ↓
│  ├─ 节点在同机房，都是自己人管？      → MySQL 主从（半同步）
│  └─ 节点跨公司，彼此不信任？          → ResilientDB / PBFT
├─ 读太慢，数据库扛不住？              ↓
│  ├─ 数据能丢（缓存）？                → Redis 主从 / Cluster
│  └─ 热到连 Redis 网络往返都想省？     → Caffeine（L1 本地缓存）
├─ 数据量 > 单机磁盘 / 写 QPS > 单机？ → 分库分表（不在本专辑范围）
└─ 搜索 / 全文检索？                   → Elasticsearch（倒排索引，不在本专辑范围）
```

## 4. 面试速查卡

### 4.1 "你学过哪些分布式系统？"

**错误回答**："我学过 Kafka 和 Redis 和 MySQL 主从。"（背名字，面试官不知道你理解了什么）

**正确回答**（30 秒）：

> "我学过四个分布式系统，它们解决的信任模型不一样——Kafka 和 Redis 主从和 MySQL 复制都在 CFT 范围内，假设节点可能挂但不会撒谎；ResilientDB/PBFT 在 BFT 范围内，防的是恶意节点。性能代价也不一样：Kafka 百万条/秒顺序写，MySQL 一万 TPS 随机写，PBFT 只有几百 TPS 因为每笔交易要三轮签名。所以选型不是选'最好的'——是选'信任假设和性能要求刚好匹配的那个'。"

这句话出来，面试官知道你不是背的——你用**信任模型**和**性能代价**两个维度把四套系统串起来了。

### 4.2 "Redis 和 MySQL 主从有什么区别？"

> "Redis 主从是性能和可用性工具——缓存丢了能重建。MySQL 主从是 durability 工具——source of truth 数据不能丢。所以 Redis 默认异步（快），MySQL 可以开半同步（等 slave 确认才返回）。一个是性能层，一个是 truth 层。"

### 4.3 "Kafka 和 MySQL binlog 有什么关系？"

> "MySQL binlog 是 Kafka 的天然上游——CDC 管道把 binlog 解析后发进 Kafka，下游各自消费。binlog 是'MySQL 帮你维护的任务队列'，Kafka 是'面向消费端的可扩展分发层'。两者在 append-only log 这个数据结构上是同构的。"
