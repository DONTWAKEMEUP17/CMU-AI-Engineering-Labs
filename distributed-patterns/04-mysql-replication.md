## 0. Motivation —— MySQL 主从和 Redis 主从看起来一样，痛点完全不同

回忆 [[03-redis-master-slave]] 的三个痛点：

```
#1 HA：master 挂了业务死
#2 读扩展：单机 QPS 顶不住
#3 数据/写扩展：单机内存装不下 / 写打不住单线程 → 要 Cluster
```

把场景换到 MySQL：单台 8 核 32G、几亿行订单数据、QPS 1 万的电商 OLTP。**主从要解决哪些痛点？**

| | 痛点 | MySQL 主从是否解决 | 备注 |
|---|---|---|---|
| ✅ | HA（master 挂了业务死） | 是 | 跟 Redis 同 |
| ✅ | 读 QPS 顶不住 | 是 | 跟 Redis 同 |
| ❌ | **单机内存装不下数据** | **不是问题** | MySQL 是磁盘 DB，**本来就不要求数据全在内存**，Buffer Pool 只缓存热点 |
| ❌ | **单机磁盘装不下数据** | **解决不了** | slave 是**完整副本**，每台装一份一样多的数据。要解决得用**分库分表**（Vitess / ShardingSphere），跟主从是不同的方案 |
| ✅ | 报表 SQL 锁表影响 OLTP | 是 | 经典玩法：**OLTP 走 master，OLAP/报表走专门一个 slave** |
| ✅ | 异地灾备（机房着火） | 是 | 跨机房 slave 是标配，叫 DR (Disaster Recovery) |
| ⚠️ | 误删数据找回 | **半对** | 主从没用（DROP 一秒同步过去）。靠**延迟 slave**（故意落后 1 小时）+ **PITR**（binlog 时间点恢复） |

### Redis vs MySQL 痛点矩阵

| 痛点 | Redis | MySQL |
|---|---|---|
| 数据量 > 单机容量 | 痛点 #3，靠 **Cluster 分片** | **不是核心痛点**（磁盘大），真不够走**分库分表** |
| 写 QPS 顶不住 | 痛点 #3，靠 **Cluster** | 极少见（MySQL 单机写 1 万 TPS 够用），真不够走分库分表 |
| 跨机房灾备 | 一般不要求（缓存挂了能重建） | **强需求**（数据就这一份，不能丢） |
| 误删恢复 | 不要求（缓存随便重建） | **强需求**（trust source 的责任） |

**一句话**：Redis 的痛点矩阵是"速度 / 容量"，MySQL 的痛点矩阵是"**不能丢、不能错、不能停**"。MySQL 是 **source of truth**，Redis 不是 —— 这是理解整章的灵魂。

## 1. 前置知识：MySQL 的内存 / 磁盘架构

要理解复制（binlog 怎么从 master 流到 slave），先要看懂 binlog 在 InnoDB 这套内存/磁盘架构里的位置。

### InnoDB 一张图

```
┌────────────────────────────────────────────────────────────┐
│                       内存（InnoDB）                         │
│                                                              │
│  ┌──────────────────┐  ┌────────────┐  ┌──────────────┐    │
│  │  Buffer Pool     │  │ Redo Log   │  │ Binlog       │    │
│  │  (默认 128MB,    │  │ Buffer     │  │ Cache        │    │
│  │   生产 32-128GB) │  │ (16MB)     │  │ (32KB/线程)  │    │
│  │                  │  └─────┬──────┘  └──────┬───────┘    │
│  │  缓存磁盘 page   │        │                │            │
│  │  (数据 + 索引)   │        │                │            │
│  │                  │        │ fsync          │ fsync       │
│  └────────┬─────────┘        │ (每事务/秒)    │ (每事务)    │
│           │                   │                │            │
└───────────│───────────────────│────────────────│────────────┘
            │ 异步刷脏           ▼                ▼
            ▼                  磁盘             磁盘
        ┌───────┐         ┌─────────┐      ┌──────────┐
        │.ibd   │         │ib_logfile│     │mysql-bin │
        │数据文件│         │redo log  │     │.000001   │
        └───────┘         │(循环写)  │     │(顺序追加)│
                          └─────────┘      └──────────┘
```

### 三块内存 + 三块磁盘各自干什么

| 组件 | 在哪 | 干什么 | 丢了会怎样 |
|---|---|---|---|
| **Buffer Pool** | 内存 | 缓存磁盘 page（数据 + 索引）。读优先看这里，没命中才读磁盘 | 不会丢数据（数据本体在磁盘）—— 只会冷启动慢 |
| **Redo log buffer** | 内存 | 事务的"物理修改"临时缓冲 | 配合 redo log 磁盘文件保证不丢已提交事务 |
| **Binlog cache** | 内存（每线程） | 事务的"逻辑命令"临时缓冲 | 配合 binlog 磁盘文件 —— **这是复制的源头** |
| **.ibd 数据文件** | 磁盘 | 真正的数据 + 索引（B+树 page） | 丢了 → 数据没了，只能从备份恢复 |
| **redo log** | 磁盘（循环写） | "数据 page 已被修改"的物理记录。**用于崩溃恢复** | 丢了 → 崩溃后未刷盘的事务全没 |
| **binlog** | 磁盘（顺序追加） | "执行了什么 SQL / 修改了什么 row"的逻辑记录。**用于复制和 PITR** | 丢了 → slave 追不上、PITR 做不了 |

### 几个困惑点的解释

**Q：为什么 MySQL 有两套日志（redo log + binlog）？看起来重复**

不重复，**职责完全不同**：

- **redo log** 是 InnoDB 引擎层的，只为 **崩溃恢复（crash recovery）** 存在 —— "我宕机重启后，buffer pool 里那些还没刷到磁盘的修改怎么找回来"。**循环写**，老的会被覆盖
- **binlog** 是 MySQL Server 层的，为 **复制 + PITR** 存在 —— "我要把这条修改告诉 slave、或者一周后用于时间点恢复"。**顺序追加，按 retention 删**

> 历史原因：InnoDB 是 Oracle 收购来的引擎，自带 redo log；MySQL Server 层需要一个引擎无关的复制基础，所以另起了 binlog。**两套日志 + 内部 XA 协调保持一致**，业内有名的痛点。
>
> 跟 [[03-redis-master-slave]] 的 "RDB + AOF 双机制" 有点相似的味道，但 Redis 是同一份数据用两种持久化策略，没有这种引擎层 / 服务层分裂。

**Q：什么算"事务已提交"？**

默认配置（`innodb_flush_log_at_trx_commit=1` + `sync_binlog=1`）下：

```
1. 修改 buffer pool 里的 page   (内存)
2. 写 redo log buffer           (内存)
3. 写 binlog cache              (内存)
4. ─── 事务 COMMIT ───
5. fsync redo log → 磁盘
6. fsync binlog   → 磁盘
7. 返回 OK 给客户端
8. (异步) 后台慢慢把 buffer pool 脏 page 刷回 .ibd 数据文件
```

第 7 步之前进程崩 → 事务回滚。第 7 步之后崩 → 重启后从 redo log replay → 数据找回来。**这就是 ACID 的 D (Durability)**。

注意：**真正"数据落盘到 .ibd 文件"是异步的**，可能事务提交几分钟后才发生。但有 redo log 兜底，业务层看不到。这套模式叫 **WAL（Write-Ahead Logging）** —— Postgres、SQLite、Kafka、LevelDB 全吃这套。

## 2. Buffer Pool 不是 Redis —— 关键澄清

很多人第一反应是"Buffer Pool 不就是 MySQL 内置的 Redis 吗"。**完全不是**，连 layer 都不一样。

### 一句话区别

> **Buffer Pool 是 MySQL 内部的"磁盘 page 缓存"，业务代码看不见**；**Redis 是独立进程的"业务对象存储"，业务代码主动用**。

### 八条对照

| 维度 | MySQL Buffer Pool | Redis |
|---|---|---|
| **是什么** | MySQL 进程内的一块内存 | **独立的进程 / 服务**，跑在自己端口 (6379) |
| **谁在用** | MySQL 引擎自己用，**业务看不见也碰不到** | **业务代码显式调用**（`redis.set` / `redis.get`） |
| **缓存的单位** | **16KB 的磁盘 page**（B+树节点 / 行 / 索引） | **任意大小的 key-value 对象** |
| **缓存什么内容** | 数据 + 索引（**就是 .ibd 文件的 page**） | 业务自己定（"用户 1000 的画像"） |
| **谁决定缓存什么** | **LRU 自动**，你不能说"这表必须留内存" | **你自己**说了算，`SET / DEL / EXPIRE` 全自由 |
| **数据源是谁** | **数据本体在磁盘 .ibd**，Buffer Pool 只是临时副本 | **Redis 内存就是数据本体**（持久化只是兜底） |
| **缓存 miss 怎么办** | **自动**去磁盘读 page，对用户透明，只是变慢 | 业务**自己回源**（去 MySQL 查、再 SET 回 Redis） |
| **挂了影响** | 重启清空，**不丢数据**（数据在磁盘） | 挂了未持久化的数据**真的没了** |

### 具体动作对比

**MySQL：`SELECT * FROM products WHERE id = 42`**

```
1. MySQL 解析 SQL
2. InnoDB 要找 id=42 的 row
3. 查 Buffer Pool：这一页在不在？
   - 在  → 直接拿走 (~50ns)
   - 不在 → 去 .ibd 磁盘读 16KB 进 Buffer Pool，再取
4. 返回结果
```

**全程业务代码完全感知不到 Buffer Pool**。它只是**性能加速器，不是数据存储**。

**Redis：用户 1000 的画像**

```
1. 业务：profile = redis.get("user:1000")
2. None? → 业务再查 MySQL → 算出来 → redis.set("user:1000", profile, ex=3600)
3. 不为 None? → 直接用
```

**业务必须显式知道 Redis 存在，自己处理 cache miss**。

### 架构图位置

```
         ┌──────────────────────────┐
         │       业务代码            │
         └──┬──────────────┬────────┘
            │              │
            │              ▼
            │       ┌─────────────┐
            │       │   Redis     │  ← 业务层缓存，业务主动管
            │       └──────┬──────┘
            │ cache miss   │
            ▼  ◄───────────┘
       ┌─────────────────────────┐
       │   MySQL Server          │
       │ ┌────────────────────┐  │
       │ │  Buffer Pool       │  │  ← 引擎内部缓存，业务看不见
       │ │  (内存)            │  │
       │ └─────────┬──────────┘  │
       │           │ page miss   │
       │           ▼             │
       │ ┌────────────────────┐  │
       │ │  .ibd 磁盘文件     │  │  ← 数据本体
       │ └────────────────────┘  │
       └─────────────────────────┘
```

**两层 cache 串起来才是生产真实形态**：业务 → Redis（miss）→ MySQL（Buffer Pool miss）→ 磁盘。这是 [[03-redis-master-slave]] "三层缓存"金字塔的雏形（再加一层进程内 Caffeine 就齐了）。

### 反问巩固

**为什么 MySQL 不"直接把整张表 LOAD 到 Buffer Pool 当 Redis 用"？**

- Buffer Pool LRU 是按 **page 访问频次**，不是业务热点
- 没有 **TTL**、没有**复杂数据结构**（List/Set/ZSet/Stream）、没有 **pub/sub**、没有 **INCR**
- 没有**独立的横向扩展能力**（扩 Buffer Pool 要扩整个 MySQL；Redis 可以独立加节点）

**Redis 是"业务层的能力"，Buffer Pool 是"DB 自己的优化手段"**。两者职责不重叠，生产里**同时存在**。

## 3. COMMIT 路径：到底几件事必须同步做完

回到 WAL：为什么 COMMIT 这么快？因为**真正等的事儿比你以为的少**。

### 演员表（一个会计的工作台比喻）

把 InnoDB 的组件映射到一个会计的工作台：

| MySQL 组件 | 大白话 | 干什么的 |
|---|---|---|
| **.ibd 数据文件** | **保险柜里锁着的总账本** | 数据真身。开柜慢，但是绝对可信 |
| **Buffer Pool** | **桌上摊开的活页夹** | 不会每查一笔都开保险柜——先把常用页拿出来在桌上改 |
| **Page（页）** | **总账本的一张纸** | MySQL 里固定 16KB 一张 |
| **Dirty page（脏页）** | **桌上被你涂改过、但还没放回保险柜的活页** | 数据已经改了，但保险柜里还是旧版本 |
| **Redo log（草稿本）** | **随身的薄草稿本**，每改一笔就写一行"账户 42 从 100 改到 80" | 唯一用途：人突然昏倒了（MySQL 崩溃），别人拿草稿本**照着重做一遍**，账不丢。**循环写**，老的会被覆盖 |
| **Binlog（业务日志本）** | **正式的业务记录本**："10:32 客户 42 取款 20" | 两个用途：①**寄副本给分行**（slave）让分行跟上；②三个月后审计要查（PITR）。**一直追加**，按 retention 删 |
| **fsync** | **不光写在纸上，还得把本子合上塞进抽屉锁好** | 写完搁桌上没用——办公室着火（机器断电）字全没 |
| **Slave 确认** | **传真给分行后，等分行回个传真说"我收到了也写下来了"** | 不回传真就不算完成 |

### 顺序写 vs 随机写

```
顺序写：                        随机写：
磁盘                         磁盘
┌────────────────┐           ┌────────────────┐
│■■■■■■■■■■■■■■■■│           │■  ■    ■      ■ │
│■■■■■■■■■■■■■■■■│           │  ■  ■■■   ■■   │
│■■■■■■■■■■■■■■■■│           │■■       ■    ■■│
│■■■■■■■■■■■■■■■■│           │  ■■■  ■       ■│
└────────────────┘           └────────────────┘
 磁头一直往后写，              磁头满盘跳→找位置→写→跳→
 不用跳，像打印机              像在贴满便签的桌上找空地
```

**草稿本（redo log）和业务日志（binlog）是顺序写**——磁头不用跳，写完一行往后挪一行。机械硬盘 ~100-200 MB/s。

**总账（.ibd 数据文件）是随机写**——B+树 page 散落在文件各处。一次 UPDATE 可能改三个索引的 page，位置完全不连续。机械硬盘 ~1-2 MB/s，差两个数量级。

> SSD 下随机写快了不少（几十 MB/s），但仍远慢于 SSD 的顺序写（几百 MB/s），因为 SSD 内部也是"先擦整块再写"。**绝对值差距缩小了，相对差距还在**。

### COMMIT 触发时，五件事谁是同步的

```
1. BEGIN
2. UPDATE products SET stock = stock - 1 WHERE id = 42
3. INSERT INTO orders (...) VALUES (...)
4. COMMIT  ← 此时触发
```

| 选项 | 大白话 | 必须同步吗 |
|---|---|---|
| **A.** 改 buffer pool 里的 page | 在桌上活页上把 100 涂掉写 80 | ✅ **必须**——不改还提交个屁 |
| **B.** redo log fsync 到磁盘 | 草稿本写"账户 42: 100→80"，**塞抽屉锁好** | ✅ **必须**（默认 `innodb_flush_log_at_trx_commit=1`）——这是 ACID 的 D |
| **C.** binlog fsync 到磁盘 | 业务日志写"客户 42 取款 20"，**塞抽屉锁好** | ✅ **必须**（默认 `sync_binlog=1`）——不写分行追不上 + 做不了 PITR |
| **D.** 脏 page 刷回 .ibd 数据文件 | **把改过的活页放回保险柜的总账本** | ❌ **不必**——这事超级慢（开柜、找位置、装订）。后台慢慢刷。崩了看草稿本重做 |
| **E.** binlog 推给 slave + 等确认 | 业务日志传真给分行 + **等分行回传真** | ⚠️ **看配置**——默认异步：不等；开半同步：等 ≥1 台回传真 |

**答案：A+B+C 必须，D 永远异步，E 看配置（默认不等，半同步才等）。**

### 这套设计的本质

为什么 D 不在 COMMIT 路径上？因为随机写慢。如果每次 COMMIT 都等数据文件更新，单机 TPS 跌 10-100 倍。

MySQL 的小聪明：COMMIT 时只**承诺**改了——草稿本写下"我承诺改了什么"，业务日志写下"我承诺业务发生了什么"，**然后立刻告诉客户成功**。真正的数据文件慢慢在后台更新。万一崩了重启后看草稿本重做。

**这就是 WAL（Write-Ahead Logging）：日志先行 → 提交立刻返回 → 数据文件慢慢追上。** Postgres、Kafka、LevelDB、SQLite 全部吃这套，是数据库最重要的发明之一。

### E 那条：异步 / 半同步 / 组复制

E 跟 A/B/C/D 不是一个维度——前者是**单机内部**的事，后者是**跨机器**的事。

| 模式 | E 怎么做 | 写延迟 | 数据丢失风险 |
|---|---|---|---|
| **异步复制（默认）** | 不等，写完本机就 OK | ~1ms | master 突然挂可能丢几毫秒数据 |
| **半同步** | 等 ≥1 台 slave 回传真 | 5-50ms | 几乎不丢 |
| **组复制 / 全同步** | 等过半 slave 回传真 | 更高 | 不丢 |

跟 Redis / Kafka 是**完全一样的 trade-off**：

```
MySQL 异步 (E 不做)     ≈ Redis 异步 (默认)     ≈ Kafka acks=1
MySQL 半同步 (E 等 1 台) ≈ Redis WAIT 1 100      ≈ Kafka acks=all
MySQL 组复制 (E 等过半)  ≈ Redis Cluster 强一致  ≈ Raft / Paxos
```

**任何分布式存储里，"一致性 vs 延迟"都长一个样。** 区别只在默认值——MySQL 异步是因为大多数业务接受"丢几毫秒换 10 倍 TPS"，金融业务才开半同步。

## 4. 三种 binlog format：各自的血泪教训

binlog 记录"这条事务做了什么"，但"做了什么"有三种记法：

| format | 记什么 | 同一条 `UPDATE users SET vip=1 WHERE id>1000` |
|---|---|---|
| **STATEMENT** | 记 SQL 原文 | `UPDATE users SET vip=1 WHERE id>1000` |
| **ROW** | 记**每一行**改前改后的值 | `row 1001: vip 0→1` / `row 1002: vip 0→1` / ... |
| **MIXED** | 默认 STATEMENT，遇到"不确定"的 SQL 自动切 ROW | |

### STATEMENT 的坑：同一条 SQL，master/slave 结果不一样

**核心问题：不确定性函数。**

```sql
-- master 上执行
UPDATE orders SET note = CONCAT(note, ' ', NOW());
```

`NOW()` 在 master 上执行的时间是 10:32:01。binlog 里记的就是这条 SQL 原文。slave 重放这条 SQL 的时候——**自己的时间是 10:32:03**。于是 slave 上 `NOW()` 返回的时间和 master 不一样，数据**永久分歧**。

类似的雷区：

| 函数 / 操作 | 为什么不确定 |
|---|---|
| `NOW()` / `CURDATE()` | 时间不同 |
| `RAND()` | 随机数不同 |
| `UUID()` | 全局唯一不同 |
| `LIMIT` 无 `ORDER BY` | 每次查出的"前 10 行"可能不同 |
| `UPDATE ... WHERE ... LIMIT N` | 同上 |
| 触发器 / 存储过程 | 内部行为可能不确定 |

MIXED 的出现就是为这个——识别到"这条 SQL 含不确定函数"就自动切 ROW。但识别不全（触发器和存储过程内部的非确定性经常漏），所以很多团队直接**一刀切全用 ROW**。

### ROW 的坑：磁盘空间和 IO 爆炸

ROW 记的是**每一行改前改后的值**。对单行 UPDATE 几乎无影响。但看这个：

```sql
-- 批量操作：删了 500 万行
DELETE FROM orders WHERE create_time < '2020-01-01';
```

| format | binlog 大小 |
|---|---|
| STATEMENT | ~100 bytes（就一句 SQL） |
| ROW | **500 万行 × 每行 ~200 bytes = ~1 GB** |

**一条 SQL 产生 1GB 的 binlog**。磁盘 IO 卡死、网络传输 slave 彻底追不上。生产里有 DBA 凌晨跑数据清理、ROW 模式 binlog 直接把磁盘打满的惨案。

**应对**：这类批量操作要**分批跑**（`DELETE ... LIMIT 10000`），让 ROW 模式产生的 binlog 可控。

### MIXED 的坑：到底切成 ROW 了没？

MIXED 的理念是"自动判断"，但 MySQL 的判断规则是**硬编码的黑名单**——它只认那几个它明确标记为非确定的函数和操作：

- 认识 `UUID()` → 切 ROW ✅
- 认识 `NOW()` → 切 ROW ✅
- **不认识你存储过程里写了个 `RAND()`** → 没切，丢了 STATEMENT ❌

所以 MIXED 看起来是"两全其美"，实际上是**生产踩坑的重灾区**。MySQL 8.0 的默认 binlog format 是 ROW——MySQL 自己拿脚投票了。

### 现状总结

| format | binlog 大小 | 一致性保证 | 生产推荐 |
|---|---|---|---|
| STATEMENT | 极小 | **有坑**（不确定函数） | ❌ 别用了 |
| MIXED | 正常时小、切 ROW 时大 | **不一定**（切不干净） | ⚠️ 有风险的妥协 |
| ROW | 大（批量操作时爆炸） | **绝对一致** | ✅ MySQL 8.0 默认，业界标准 |

> 写本章时 MySQL 8.0 已是主流，`binlog_format=ROW` 是唯一推荐。STATEMENT/MIXED 更大的价值是**历史课**——让你理解为什么分布式复制里"逻辑语句"不够、"行级变更"才是安全的。
