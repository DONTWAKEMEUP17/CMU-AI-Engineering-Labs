# 02 · ResilientDB / PBFT — 不信任的节点之间怎么达成共识

> **本章状态：成稿。**

## 本章要回答的核心问题

1. 为什么 Kafka / Redis / MySQL 的复制机制在某些场景下不够用？—— **信任模型的区别**：你以为同事只是睡着了，但他可能在撒谎
2. 拜占庭将军问题到底在讲什么？—— 不是历史课，是分布式系统里**最贵的那个假设**
3. PBFT 三轮投票（pre-prepare → prepare → commit）每一步在防什么？—— 会议室举手三轮，每一轮防不同的花招
4. ResilientDB 在 PBFT 之上加了什么？—— GeoBFT 跨地域、RingBFT 环形共识、SpotLess 无领导
5. 跟你前面学的东西怎么串起来？—— Kafka/Redis/MySQL 都假设节点是**诚实的**；BFT 是当这个假设不成立时的答案

## 0. Motivation — 一个故事：六个将军围一座城

### 0.1 将军们的困境

六个将军各带一支军队，围住了一座城。他们必须**同时进攻**才能取胜——如果只有一半人冲上去，那就是送死。

但问题来了：将军们彼此之间只能靠信使传话。而且——**有些将军是叛徒**。

叛徒会干什么？

- 给 A 将军传"明早 6 点进攻"，给 B 将军传"明早 8 点进攻"
- 假装没收到消息
- 跟另外两个叛徒串通好一起投假票

如果将军们只能简单投票（"我同意 6 点进攻"），叛徒可以轻松让诚实的将军们达不成一致——有人冲、有人不冲，全军覆没。

**这就是拜占庭将军问题（Byzantine Generals Problem）**。

### 0.2 分布式系统里的"将军"和"叛徒"

翻译成你熟悉的语言：

| 故事里 | 分布式系统里 |
|---|---|
| 将军 | 一个节点/服务器 |
| 进攻时间 | 要达成共识的值（比如"下一笔交易的顺序"） |
| 信使 | 网络消息 |
| 叛徒 | **拜占庭故障节点**——不只是挂了，而是**在作恶** |
| 诚实的将军 | 正常节点 |

### 0.3 为什么前几章的机制在这里不够用

回到 [[03-redis-master-slave]] 和 [[04-mysql-replication]]：Redis 主从复制、Kafka partition replication、MySQL 半同步——它们都假设什么？

**节点可能挂（crash）、可能慢、可能断网——但不会撒谎。**

Redis slave 不会对 master 说"我收到了"但实际上没写。MySQL slave 不会伪造 binlog 位点。Kafka follower 不会篡改消息后还跟 leader 说"我跟你一致"。

这个假设叫 **CFT（Crash Fault Tolerance，崩溃容错）**。前四章的所有复制机制，全在 CFT 范围内。

但有些场景下，节点**会**撒谎：

- **区块链**：任何人都能跑一个节点。有人有动机篡改交易记录偷钱
- **跨机构金融清算**：A 银行和 B 银行是对手方。A 银行没有理由信任 B 银行的服务器
- **供应链溯源**：多个公司共享一份数据，每家都可能篡改对自己不利的记录
- **跨云/跨管理域**：AWS 上的节点和阿里云上的节点，不属于同一个信任域

这时候 CFT 不够用。你需要 **BFT（Byzantine Fault Tolerance，拜占庭容错）**——即使一部分节点在作恶，系统仍然能达成正确的共识。

## 1. CFT vs BFT：两种信任模型，两种代价

### 1.1 一个表看清楚

| | CFT（崩溃容错） | BFT（拜占庭容错） |
|---|---|---|
| **假设** | 节点可能崩、慢、断网，但**不会故意撒谎** | 节点可能**恶意**伪造消息、串通、选择性响应 |
| **典型场景** | 同一家公司内部的服务、同一个管理域 | 跨组织、区块链、多对手方 |
| **容错数** | 2f+1 节点容 f 个崩 | **3f+1** 节点容 f 个作恶 |
| **消息轮数** | 2 轮（leader propose → follower ack） | **3 轮**（pre-prepare → prepare → commit） |
| **需要签名吗** | 不需要 | **每轮都要**数字签名，防止伪造 |
| **代表协议** | Raft / Paxos / Zab | PBFT / HotStuff / Tendermint |
| **你前面学过的** | Kafka / Redis / MySQL 复制 | — |
| **复杂度** | 低 | **指数级上升** |
| **性能** | 几千~几万 TPS | 几百~几千 TPS（同样的硬件） |

### 1.2 为什么 BFT 要 3f+1 而不是 2f+1

CFT（比如 Raft）用 2f+1 = 5 个节点就能容 2 个崩。BFT 要 3f+1 = 7 个节点才能容 2 个作恶。

直觉解释：**崩溃的节点是"不说话"的，作恶的节点是"说谎话"的。** 不说话你只需要多数派就够了（5 个里 3 个同意就过）。说谎话你要防备"叛徒给不同人发不同消息"——需要更多的诚实节点来压倒叛徒。

**一句话：CFT 是在跟"沉默"斗，BFT 是在跟"谎言"斗。斗谎言的代价天然更大。**

## 2. PBFT：会议室举手三轮，每轮防不同的事

PBFT（Practical Byzantine Fault Tolerance，Castro & Liskov 1999）是第一个**实际可用的**拜占庭容错协议。它把"防撒谎的共识"拆成了三个阶段。

### 2.1 角色

- **一个 leader（主节点）**：负责提出议案（"我提议这个顺序"）
- **其余 replicas（副本节点）**：对议案投票
- **客户端**：发起请求，等结果

### 2.2 三轮投票 —— 会议室比喻

假设一个会议室里有 7 个人（3f+1，f=2），其中最多 2 个可能是骗子。他们要对一个提案达成一致。

**Pre-prepare（第一轮——"大家都听到老板说的了吗"）**

```
leader：我提议，第 100 号交易是"A 给 B 转 10 块钱"
       ↓ 群发所有人
每个人检查：这确实是 leader 说的吗？leader 有没有给不同人说不同的话？
```

防什么：**leader 本身就是叛徒**，给 A 说"A→B 转 10 块"，给 B 说"A→C 转 10 块"。如果 leader 真这么干，第一轮就被诚实节点发现了——他们收到的 pre-prepare 消息不一样。

**Prepare（第二轮——"我听到的是 X，你们听到的也是 X 吗"）**

```
所有人互相广播："我收到 leader 的提案是：A→B 转 10 块"
每个人收别人的 prepare：超过 2/3 的人说的是同一件事吗？
```

防什么：**叛徒节点在第一轮假装听了 leader，但这一轮给不同人说不同的话**。因为 prepare 是所有人广播所有人的，每个诚实节点能自己统计"多数人说的是什么"。

**Commit（第三轮——"我确认大家都确认了，执行"）**

```
所有人再广播一次："我确认 2/3 的人同意 A→B 转 10 块"
收到 2/3 的 commit → 执行交易 → 回复客户端
```

防什么：**前两轮有人过了但第三轮反悔**，或者**网络延迟导致部分节点先执行但另一部分没收到足够确认**。第三轮保证"每个人都知道别人也知道"——共识的"共识"。

### 2.3 客户端等多久

客户端发出请求后，等 **f+1 个一致回复**（不是 2f+1 也不是所有）。为什么 f+1 就够了？因为 f+1 个里**至少有一个是诚实的**——那个诚实节点确认"已经达成了 2f+1 共识"，这个信息可靠。

### 2.4 一句话

> PBFT 三轮投票的本质：**第一轮防 leader 撒谎，第二轮防追随者撒谎，第三轮防有人中途反悔。** 每多一轮，多防一种恶意行为。这就是 BFT 比 CFT"消息多、签名多、慢"的根本原因。

## 3. PBFT 的痛点 — 为什么后来出了那么多改进版

### 3.1 PBFT 最大的问题：消息量是 O(N²)

三轮投票，每轮所有人都给所有人发消息。7 个节点 → 一轮 prepare 就是 7×6 = 42 条签名消息。三轮下来超 100 条。如果有 100 个节点 → 一轮就接近 10,000 条消息。

**PBFT 的节点数几乎不能超过 20 个**。不是理论上不行，是消息量撑不住。

所以后来的改进版都在解决这个问题：

| 协议 | 怎么减消息 |
|---|---|
| **HotStuff**（2019，被 Libra/Diem 采用） | 把三轮消息收拢到 leader 中转——O(N) 而不是 O(N²) |
| **Tendermint**（Cosmos 用） | 两轮就够（propose → prevote → precommit），但前提是每轮超时前没看到冲突 |
| **DAG-BFT**（Narwhal/Tusk） | 不按"一轮轮"组织，用 DAG 拓扑——不同节点同时提出不同区块，并行确认 |

### 3.2 ResilientDB 走的路

ResilientDB 不是一个协议，是一套**共识协议家族**。它在 PBFT 之上加了几个变体：

| 协议 | 场景 | 核心思路 |
|---|---|---|
| **PBFT** | 基线 | 经典三轮投票 |
| **GeoBFT** | 跨地域（比如北京→纽约→法兰克福） | 每个地域内部先达成局部共识，再跨地域通信——**减少跨海光缆上的消息数** |
| **RingBFT** | 追求吞吐 | 节点排成环形，消息只沿环传而不是全广播——O(N) 消息量 |
| **SpotLess** | 防"静默攻击" | leader 假装正常但**选择性忽略**某些请求——SpotLess 无 leader，轮流提议，防 leader 做恶 |
| **RCC（Resilient Concurrent Consensus）** | 高并发 | 多个共识实例并行跑，不同交易组独立共识 |

ResilientDB 的定位不是"另一种 PBFT 实现"，而是**"PBFT 在实际场景下的 N 种工程变体"**——根据你需要的是跨地域、高吞吐、还是防静默攻击，选不同的协议变体。

## 4. 跟你前面学的东西串起来

### 4.1 信任模型从低到高

```
信任谁           →   你挑哪个协议

节点不会死         →   不需要复制（单机 MySQL）
节点可能挂         →   CFT（Raft / Kafka / Redis 主从 / MySQL 半同步）
节点可能骗你       →   BFT（PBFT / HotStuff / ResilientDB）
任何人都不信任     →   区块链（PoW / PoS + 经济激励）
```

你在 [[01-kafka-pub-sub]]、[[03-redis-master-slave]]、[[04-mysql-replication]] 里学的所有东西都停在第二层。本章讲的第三层——不是"更好的复制"，而是**完全不同的信任假设**。

### 4.2 为什么抖音不用 PBFT 做主从复制

因为没必要——代价太高。PBFT 每笔交易要多轮签名、O(N²) 消息量、TPS 比 Raft 低一个数量级。抖音的 MySQL slave 在同一机房、同一管理域、是同事管的——没有动机撒谎。

**BFT 是为"你不信任对方"的场景准备的**。你信任自己的 MySQL slave 不会篡改数据——它没有收益。你的 CPU 不会故意算错 1+1=3。所以 CFT 够用。

但如果你的系统是"A 公司和 B 公司之间做清算"、"任何人在网上都能跑一个节点"、"三个云厂商各自维护一个副本"——那你就有可能遇上"对方有动机篡改数据"的情况。这时候才值得为 BFT 付那笔更高的成本。

### 4.3 全书横向锚点

| 章节 | 协议/系统 | 信任模型 | 关键机制 |
|---|---|---|---|
| ch01 | Kafka | CFT | partition + replication + ISR |
| ch02 | ResilientDB/PBFT | **BFT** | 三轮投票 + 数字签名 |
| ch03 | Redis 主从 | CFT | 异步复制 + WAIT |
| ch04 | MySQL 复制 | CFT | binlog + 半同步 + GTID |

## 5. 最小自测

读完本章，你应该能回答：

1. CFT 和 BFT 的根本区别是什么？（一句话：一个假设节点只会挂，一个假设节点可能作恶）
2. 为什么 PBFT 要三轮而不是两轮？（每轮防不同的人撒谎：leader → 追随者 → 有人反悔）
3. 为什么需要 3f+1 而不是 2f+1？（作恶节点"说谎"，比"不说话"更难对付）
4. 为什么大多数互联网公司不用 BFT？（因为节点在同一管理域，没有作恶动机，CFT 够用还便宜）
5. ResilientDB 不是"一个协议"——它是一套什么？（共识协议家族：PBFT / GeoBFT / RingBFT / SpotLess，不同场景选不同变体）
